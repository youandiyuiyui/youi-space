## 4. やり残し・課題

### 4-0. 画面の穴（最優先・ほかの人の画面で好きな処理を動かせる）
画面のボタンの `onclick="…('…')"` の文字の中に、利用者が決められる文字をそのまま入れている所がある。`escapeHtml()` は `'` を変換しないうえ、ボタンの属性の中では変換した文字が元に戻るので、守れていない（約束は `AGENTS.md`「壊してはいけない約束」）。

| 記号 | 何が起きるか | 起きる条件 | 場所 |
|---|---|---|---|
| S1 | 「お礼を決める」シートの「ありがとうを伝える」ボタンに、相手の名前（`deals` の `byName`／`otherName`）を入れている。ニックネームに `'` を入れた人（例：`');alert(1)//` は13文字で、20文字の上限に収まる）が「終わりました」を押すと、相手がこのボタンを押したときに、相手の画面で好きな処理が動く。悪気のない `'` 入りのニックネームでも、ボタンが効かなくなる | **ふつうの画面からでも起きる** | `index.html` の `openGateSheet()` |
| S2 | 掲示板のカード・投稿の詳細・「お礼を決める」シートに、投稿や記録の ID（`p.id`・`d.id`）を変換せずに入れている。ID は作った人が好きに決められ（`/` 以外の文字が使える）、ルールでも調べていない。そういう ID の投稿を作られると、掲示板でそのカードを押した人の画面で好きな処理が動く | 改造した端末から作ると起きる | `index.html` の `openPostDetail(` を呼ぶ所（`renderPostCard` など）・`editPost(`・`confirmDeletePost(`・`skipThanks(` を呼ぶ所、`firestore.rules` の `posts`・`deals` |

直し方の候補：
- onclick には一覧の番号（`list[i]` の `i`）かログインの uid だけを渡し、名前や ID は `window.__deals`・`window.__rawPosts` などから引き直す（`openChatMenu()` の `window.__reportName` と同じ形）。
- ルールで、ID を自動で付く形（英数字20文字：`postId.matches('^[A-Za-z0-9]{20}$')`）に限る。アプリは `add()` で自動の ID を使っているので、ひとつ前の版とも両立する。
- `deals` の `byName`・`otherName`・`title` を `str(…, 60)` にする（いまのアプリも60文字以内しか書かない）。
- すでに変な ID や名前のデータがないか、運営がコンソールで確かめる。
- 直したら、`'` を含むニックネームのケースを `tests/e2e/` に、変な ID が拒否されるケースを `tests/rules.test.mjs` に足す。

### 4-1. ルールで塞げていない穴（優先度：高）

| 記号 | 起きる条件 |
|---|---|
| G2・G6・N1・N2・N3・N5 | ふつうの画面では起きない。改造した端末（ブラウザの開発ツールなど）から直接データを書くと起きる |
| G4・G5・N4 | **ふつうの画面でも起きる**。投稿の「メッセージを送る」で会話を開くと、メッセージを1通も送らないうちから「終わりました」と「お礼を伝える」（右上のメニュー）を押せる。ブロックされた人も同じことができる |

| G2 | ＆ポイントを、残高を超えて何度でも手渡せる（受け取った人の残高も増える） | `firestore.rules` の `thanks` | ルールは記録を足し上げて合計を出せない。①手渡した合計を数字で持ち、お礼と同じ書き込みで、ちょうど `points` だけ増えたことをルールで確かめる（受け取った分は入らないので、上限は「決まった額」か「毎月戻る枠」になる。下の注意） ②Cloud Functions（有料プラン）でサーバー側で計算する |

| G6 | 災害モード中でも、端末が `disaster: false` と書けば、ふだんの記録として信頼の段階に加点される（災害モード中の記録は加点しない決まり。いまのルールは `disaster` の値を確かめていない） | `firestore.rules` の `thanks`・`deals` | `disaster` が運営の設定（`config/disasterMode` の `active`）と同じ値かを確かめる（true も false も）。下の注意 |
| N1 | 名前を伏せた頼みごとの投稿者に、「伏せない会話」（`masked` なし）を作って話しかけられる。作った人は、投稿者の公開プロフィール（ニックネーム・自己紹介・本人確認済みの印）を読める（名前つきの投稿をしたことがない人でも）。投稿者の端末はふつうの会話として扱うので、返信するとニックネームも相手に届く | `firestore.rules` の `conversations`（作るときに `masked` を確かめない）・`profiles`（`seesViaConv`）。`masked` を書くのは話しかける側の端末（`messageFromPost`・`sendChat`） | 会話を作るとき、相手が名前を出して投稿した人（`profiles` の `listed` が true）でなければ、相手を `masked` に入れることを必須にする（`get()` で確かめる）。公開プロフィールがまだ無い人の扱いを先に決め、ひとつ前の版からの送信が拒否されないかテストで確かめる。`index.html` の `/* ===== 公開プロフィール` のコメント「画面でもルールでも開けない」も直す |

| N4 | ブロックで止まるのは、ブロックした人の画面に相手の投稿と会話を出さないこと（その会話も開けない）と、ブロックされた人が公開プロフィールを読めないことだけ。ブロックされた人には何も知らされず、会話の画面から「終わりました」（ブロックした人のゲートに入り、決めるまで「困っていること」を出せない）と、ありがとう（感謝タグと「ひとこと」がブロックした人の「よく言われること」に出る）を、そのまま送れる。メッセージも送れる（ブロックした人の画面には出ない） | `index.html` の `openDeals()`・`renderWords()`（`isBlocked()` を使っていない）、`firestore.rules` の `deals`・`thanks`・`messages` | 画面で、ブロックした相手との記録をゲートと「よく言われること」に入れない。ルールでも止めるなら、`profiles` の `notBlocked()` と同じく `get()` で相手の `users` の `blocked` を見る。ただし、ルールで断るとブロックされた人の画面にエラーが出て、ブロックに気づかれるおそれがある（案内には「相手に通知はされません」とある）。どちらにするかは運営と決める |

**G2 の候補①の注意**
- 残高は「300pt ＋ 受け取った分 − 手渡した分」。①で確かめられるのは手渡した分だけで、受け取った分は相手の側の記録（送る人は相手の `users` に書けない）。①だけでは「残高を超えない」ことまでは確かめられない。
- ①で作れる上限は、決まった額（例：300pt）か、毎月戻る「渡す枠」（設計書 §5.6・§11 の `giftBudget`）。どちらも＆ポイントの仕組みが変わるので、運営と決めてから作る。
- この数字は確かめるためだけに使う。画面の残高は、これまでどおり `thanks` から計算する（`AGENTS.md` の「残高は `users` に持たない」は変えない）。
- すでにいる利用者がこれまでに手渡した合計（最初の値）は、ルールでは確かめられない。どう入れるかを決める。
- `users` は本人が消して作り直せる（退会のため）ので、そこに数字を置くと0に戻せるおそれがある。置き場所も考える。
- `users` の `points` 項目と、それを「減らすことだけ許す」ルールは v0.5.0 の名残。v0.5.1 からアプリはこの項目を書いておらず、いまは何も守っていない。

**G4 の補足**
- 作られた側が外す方法：そのたびに「今回は伝えない」を押すか、「いま急ぎです（24時間おやすみ）」を使う。
- 信頼の段階の計算にも、1件ごとに +0.5 が入る（段階は本人にしか見えないので、影響は小さい）。
- いまの `deals` は、作ったあとに書き換えられない。相手が「確かめた」と足すことだけができる書き換えをルールに足す。作るときの項目は変えない（ひとつ前の版の「終わりました」が失敗しないように）。
- ゲートと段階は端末（`openDeals()`・`computeTrust()`）が数えているので、ルールだけ変えても効かない。アプリも「相手が確かめた記録だけ数える」に変える。古い版の端末は、更新されるまで、すべての記録を数える。
- 「会話がある相手に限る」だけでは足りない。会話は片方だけで作れ、ふつうの画面でも1通送ればできる。

**G5 を直すときの注意**
- `deals` は `exists()` で探せない（ID が自動で付くため）。確かめられるのは、お礼に入っている `dealId` の記録を `get()` で読み、2人が入っているかだけ。会話のメニューから贈るお礼（`thanksToPartner()`）は、`dealId` が空。
- 会話や `deals` が「ある」だけでは、やり取りの証にならない（どちらも片方だけで作れる）。複数のアカウントを持つ人には効かない。
- 会話の文書は、最初のメッセージを送ったときにできる（`sendChat()`）。v0.5.4 までの画面は、会話を開いた直後から「お礼を伝える」を押せるので、会話の文書を必須にすると古い版ではこの操作が失敗する。
- 候補：①（すぐできる・ひとつ前の版とも両立）`pairKey` が、2人の uid を並べ替えて `_` でつないだもの（`convIdFor` と同じ形）と同じかを確かめる ②（G4 のあと）`dealId` があるお礼は、その `deals` を `get()` で読んで確かめる（ルールのテストの `thanksDoc` は、無い記録 `d1` を使っているので直す）③会話に「それぞれが書いた」印を持たせる（いつから必須にするかは運営と決める。画面も最初のメッセージの前はお礼を出さないようにそろえる）。

**G6 を直すときの注意**
- 得をするのは「災害モード中に false と書く」ほう。「有効なときだけ true を許す」では足りない。設定と同じ値かを確かめる。
- `config/disasterMode` は本番にあるとは限らない。無い文書を `get()` して中を読むとエラーになり、お礼と「終わりました」がすべて拒否される。先に `exists()` で確かめ、無いときは平時（false）として扱う（設計書のルール例 `disasterNow()` はこの点が抜けているので、そのままは使わない）。
- `tests/rules.test.mjs` は、はじめに `config/disasterMode`（`active: false`）を入れている。文書が無い場合のケースも足す。

### 4-2. 分かっている制約（Cloud Functions が要る）
- 名前を伏せた投稿にも投稿者の uid が残る。同じ人の名前つき投稿と結び付けられてしまう。名前を伏せた会話でも相手には uid が分かるので、伏せている人が名前を出して投稿したことがあると（`listed` が true）、公開プロフィールも読めてしまう（画面では開かないようにしている。v0.5.3 の PR の「ルールでも開けない」は、正しくは「画面では開けない」）。
- 感謝を受け取った人には、贈った人の uid と時刻がデータ上は見える（画面には送り主の名前を出さない。届いた日の出し方は §4-3）。
- どちらも、有料の Blaze プランにして Cloud Functions でサーバー側の処理を足せば解決できる。費用の判断は運営が行う。

## 6. ChatGPT の使い方

### できること・できないこと
| できる | できない |
|---|---|
| 機能の相談・設計・優先順位づけ | アプリやテストを動かす |
| 画面の文言・説明文・PR の説明の下書き | リポジトリに書き込む |
| ルールや設計の考え方のレビュー | （GitHub をつながないとき）最新のコードを読む。入れたファイルの時点の内容で考える |

ChatGPT が書いたコードは、そのまま入れない（GitHub の画面から main にアップロードもしない）。Codex（か Claude Code）でテストを通してから、PR で入れる。

1. ChatGPT で「プロジェクト」を作る（名前の例：You&i Space）。

   - §5 の資料（戦略指針・概念ノート・ルールブック・内部の設計メモ）
   - `index.html` は約4,900行と大きい。相談したい部分だけを貼るほうが確実
3. プロジェクトの指示に、下の文を貼る。
4. リポジトリの `AGENTS.md` や `docs/handoff.md` が変わったら、プロジェクトのファイルも入れ替える。
5. （任意）ChatGPT に GitHub をつなぐと、リポジトリの今の中身を、その都度読んで答えられるようになる。
   - つなぎ方：ChatGPT の設定 →「プラグイン」（画面によっては「アプリ」）→ GitHub。GitHub の画面に移るので、ChatGPT のアプリを入れ、読めるリポジトリに `youandiyuiyui/youi-space` を選ぶ。
   - 使い方：相談するとき、入力欄の「＋」から GitHub を選ぶか、「GitHub の youi-space の index.html を見て」のように頼む。
   - プランや画面によっては使えないことがある。そのときは手順2・4のとおりファイルを入れる。つないだあとも、`AGENTS.md` と `docs/handoff.md` はプロジェクトのファイルに入れておく。

## 7. Codex の使い方

### 準備（最初の一回・クラウド）
Codex のクラウドは、ChatGPT の有料プランで使える（順に広げている途中なので、まだ出ていないこともある）。2026年9月末に、環境の作り方が新しくなった。

1. ChatGPT（ウェブかデスクトップアプリ）で新しい依頼を開き、「Work in」→「Cloud」→「Select environment」→「Create environment」と進む。
2. リポジトリ `youandiyuiyui/youi-space` を選ぶ（GitHub をつなぐよう出たら、つなぐ）。名前の似た `You-i-Space-two` は別の試作なので選ばない（§5）。
3. 「Get started」を押す。Codex がリポジトリを調べて、テストの準備を進める。途中の会話で、次のように頼む。
   ```
   インストールスクリプト（Install script）は bash tests/setup.sh にしてください。Node.js は 20 以上、Java は 21 以上にしてください。
   そのあと cd tests && npm test が通るか確かめてください。
   ```
   - `tests/setup.sh` は、テストに要るもの（Node.js の部品・Firestore エミュレーター・Chromium・通し確認で使う旧アプリ）をまとめて取ってくる。Java 21 以上が無いときは、入れられる環境なら入れる（入れられなければ「Java 21 以上が要ります」と出て止まる）。
4. 最後に出る報告（setup report）で、次の2つを確かめる。
   - `npm test` が通ったか（ルール116件・通し確認107件・デモ36画面）

## 9. 運営の操作（Firebase コンソール・くわしい手順）
`AGENTS.md` の「運営の操作」のくわしい説明。エージェントはコンソールを操作できないので、運営が行う。

| 操作 | 手順 | 気をつけること |
|---|---|---|
| ルールの公開 | Firestore Database → ルール に `firestore.rules` を丸ごと貼り付けて「公開」 | 公開したら、ルールの3行目の版が PR に書かれたとおりか見る。コンソールで直接書き換えたときは、同じ変更を `firestore.rules` にも入れる（次に丸ごと貼ったときに消えるため） |
| 本人確認の申請を見る | `users` で `verifyRequested` が true で、`verified` がまだ無い人が申請中（日時は `verifyRequestedAt`、連絡先は同じ文書の `email`） | アプリは「運営からメールでご連絡します」と案内しているので、メールで連絡し、対面かオンラインで身分証を見せてもらう（画像はアプリに保存しない）。見送るときは、もう一度申請できるように `verifyRequested` を消す（本人の端末からは消せない） |
| 本人確認済みにする | `users/{uid}` に `verified: true` | 本人が次にアプリを開いたとき（ログインしたままでも）、公開プロフィールにも印が付く。ニックネームをまだ決めていない人は、決めたときに付く。すぐ出したいときは、`profiles/{uid}` があれば、その `verified` も true にする（無いときは作らない） |
| 災害モードにする | `config/disasterMode` に `{ active: true, scope: '対象の地域' }` | `scope` はお知らせの帯に出す言葉だけ（無いか `'all'` なら「全域」）。地域で分ける仕組みはなく、`active` が true のあいだは全員が災害モードになる。そのあいだはお礼の確認（ゲート）がお休みになり、「終わりました」とお礼には `disaster: true` が付いて、結びの段階の計算に入らない（あとから直せないので、間違えて入れない） |
| 災害モードを終える | `active: false` にする（文書を消してもよい） | |
| 通報・少し気になったを見る | `reports` と `concerns` を見る | |
| インデックスを作る | PR の説明に手順が書いてあるときだけ。Firestore Database → インデックス で、書かれたとおりのコレクション・項目・並び順で作る | できあがるまで少し時間がかかることがあるので、できてからマージする |

## 付録A. ルールを変えたときの両立の確かめ方（コマンドの例）
`AGENTS.md`「ルールを変えたときの、両立の確かめ方」の3つの組み合わせを確かめる例。リポジトリのいちばん上で動かす。`/tmp/youi-prev` は作業用の場所。2つめと3つめは、失敗で終わるのが想定どおりのこともある（何件落ちたかを PR に書く）。
```
git show origin/main:firestore.rules > /tmp/main.rules
(cd tests && RULES=/tmp/main.rules npm run test:rules)        # 新しいルールのテスト × 公開中のルール

git worktree add --detach /tmp/youi-prev origin/main            # 公開中の版の作業用コピー
ln -s "$PWD/tests/node_modules" /tmp/youi-prev/tests/node_modules
cp firestore.rules /tmp/youi-prev/firestore.rules
(cd /tmp/youi-prev/tests && npm run test:e2e)                   # 公開中のアプリ × 新しいルール

cp index.html /tmp/youi-prev/index.html
cp -r tests/e2e /tmp/youi-prev/tests/
cp /tmp/main.rules /tmp/youi-prev/firestore.rules
(cd /tmp/youi-prev/tests && npm run test:e2e)                   # 新しいアプリ × 公開中のルール

git worktree remove --force /tmp/youi-prev                      # 片づけ
```
- `origin/main` が無い環境（Codex のクラウドなど）では、インターネットにつないで `git fetch origin main` を先に動かす。
