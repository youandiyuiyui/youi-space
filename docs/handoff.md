| 項目 | 内容 |

| 何のアプリか | 地域の支え合いのアプリ。「支援者支援」が軸（支える人ほど頼る回路が塞がれるので、その回路をこちらから作りに行く） |

| 試し方 | ログイン画面の「ゲストで試す」で、何も送信しないデモが動く |

## 4. やり残し・課題

### 4-1. ルールで塞げていない穴（優先度：高）
ふつうに画面を使う分には起きない。ただし、改造した端末（ブラウザの開発ツールなど）から直接データを書くと起きる。実証の参加者が増える前に塞ぎたい。

| 記号 | 何が起きるか | 場所 | 直し方の候補 |
|---|---|---|---|
| G2 | ＆ポイントを、残高を超えて何度でも手渡せる（受け取った人の残高も増える） | `firestore.rules` の `thanks` | ルールは合計を計算できない。①手渡した合計を `users` に持ち、同じ書き込みでルールが突き合わせる ②Cloud Functions（有料プラン）でサーバー側で計算する |
| G4 | 相手の同意なしに「終わりました」の記録（`deals`）を作れる。作られた側は、決めるまで新しい「困っていること」を出せなくなる（ゲート。最長72時間） | `firestore.rules` の `deals`、`index.html` の `/* ===== ゲート` | 相手側の承認を足す（2人が揃ってはじめて有効）、または実際に会話がある相手に限る |
| G5 | やり取りのない相手にも、ありがとう（＆ポイント）を贈れる | `firestore.rules` の `thanks` | 会話か `deals` がある相手に限る（`exists()` で確かめる） |
| G6 | 有事の印（`disaster`）を、端末が自分で付けている | `firestore.rules` の `thanks`・`deals` | `config/disasterMode` が有効なときだけ true を許す（`get()` で確かめる） |

直すときは `AGENTS.md` の「反映の順番」に従い、ひとつ前の版のアプリと両立させる。`tests/rules.test.mjs` に悪用のケースを足す。

### 4-2. 分かっている制約（Cloud Functions が要る）
- 名前を伏せた投稿にも投稿者の uid が残る。同じ人の名前つき投稿と結び付けられてしまう。
- 感謝を受け取った人には、贈った人の uid と時刻がデータ上は見える（画面では週まとめにして伏せている）。
- どちらも、有料の Blaze プランにして Cloud Functions でサーバー側の処理を足せば解決できる。費用の判断は運営が行う。

### 4-3. 確かめること・決めることが残っているもの
| 項目 | 状態 | 次にすること |
|---|---|---|
| 本物の Firebase での確認 | v0.5.0 のときに「マージ後に実アカウントで一度ログインして確認が必要」とされた。以降はエミュレーターで確かめている | 運営が実アカウントで、登録・投稿・会話・お礼・プロフィールを一通り試す。済んだらこの行を消す |
| ＆ポイントの引き換え（実アカウント） | 準備中（デモだけで体験できる） | 協賛店の精算の方法・＆ポイントの法的な位置づけ（専門家の確認が必要）を決めてから作る |
| 評価経済の設計（寄り合い・町のつみたて・信頼の段階の使い方など） | 設計書の PR #6 は閉じた。中身は運営の内部の設計メモに統合済み。元の設計書は git の `9c5395b`（`docs/evaluation-economy.md`）に残っている | 進めるときは、運営から内部の設計メモを受け取る |

コードのコメントで「正本」として名前が出てくるが、リポジトリには入っていない。新しいエージェントに設計の相談をするときは、運営が渡す。

|---|---|---|
| 戦略指針 | §5-1「三つの入口」、§5-6「評価経済」 | `index.html` の v0.3.0・v0.4.0 の見出しコメント |
| 概念ノート | §3「頼む前に、渡す」 | `index.html` の v0.3.0 の見出しコメント |
| 内部の設計メモ（評価経済） | PR #6 の設計書を統合したもの | §4-3 |
| 公式サイト | You&i Space の説明（支援者支援・役割の循環・平時から災害時へ） | https://youandiyuiyui.github.io/youi-website/ |
| Firebase コンソール | 本番のルール・データ・運営の操作 | 運営だけが入れる |

## 6. ChatGPT の使い方

### できること・できないこと
| できる | できない |
|---|---|
| 機能の相談・設計・優先順位づけ | アプリやテストを動かす |
| 画面の文言・説明文・PR の説明の下書き | リポジトリに直接書き込む |
| ルールや設計の考え方のレビュー | 最新のコードを自動で読む（入れたファイルの時点の内容で考える） |

ChatGPT が書いたコードは、そのまま入れない。Codex（か Claude Code）でテストを通してから入れる。

### 準備（最初の一回）
1. ChatGPT で「プロジェクト」を作る（名前の例：You&i Space）。
2. プロジェクトのファイルに、次を追加する。
   - `AGENTS.md`（約束・手順）
   - `docs/handoff.md`（このファイル）
   - 必要に応じて `firestore.rules`（ルールの相談をするとき）
   - §5 の資料（戦略指針・概念ノート・内部の設計メモ）
   - `index.html` は約4,900行と大きい。相談したい部分だけを貼るほうが確実
3. プロジェクトの指示に、下の文を貼る。
4. リポジトリの `AGENTS.md` や `docs/handoff.md` が変わったら、プロジェクトのファイルも入れ替える。

### プロジェクトの指示（コピー用）
```
あなたは「You&i Space」の開発と運営を手伝う相談役です。You&i Space は、You&i（結）が運営する地域の支え合い（支援者支援）のアプリで、いまは同意を得た人だけが使う限定実証版です。

【前提】
- 約束・手順は、プロジェクトのファイル AGENTS.md が正本です。経緯・いまの状態・やり残しは handoff.md にあります。答える前に、関係するところを確かめてください。
- AGENTS.md の「壊してはいけない約束」（本名を見せない・名前を伏せた人を守る・＆ポイントの残高は thanks から計算する・低い評価や点数を他人に見せない など）に反する案は出さないでください。反しそうなときは、そう指摘してください。
- アプリの文言は、やさしい日本語にして専門用語を避けます。
- コードの変更は Codex がテストを通してから入れます。コードを書くときは、そのまま Codex に渡せるように「変えるファイル・変える理由・確かめるテスト」を添えてください。
- データの持ち方（Firestore のルール）が変わる案では、「先にルールを Firebase コンソールで公開 → そのあとアプリを公開」という反映の順番と、ひとつ前の版のアプリとの両立に触れてください。

【答え方】
- 日本語で、見出し・箇条書き・表を使って、あとから確認・編集しやすい形にしてください。
- 依頼があいまいなとき、または条件が足りないときは、作り始める前に「A・B・C のどれにしますか」のように選択肢を示して質問してください。
- ファイルに書かれていないことは推測で埋めず、「ファイルからは分からない」と書いてください。
```

## 7. Codex の使い方

### 準備（最初の一回）
1. Codex に GitHub をつなぎ、リポジトリ `youandiyuiyui/youi-space` の環境を作る。
2. 環境の設定にある「セットアップスクリプト」に、次の1行を入れる。
   ```
   bash tests/setup.sh
   ```
   - テストに要るもの（Node.js の部品・Firestore エミュレーター・Chromium、なければ Java）を、ここでまとめて取ってくる。
   - 準備が済めばテストはインターネットなしで動くので、作業中のインターネット接続はオフのままでよい。
   - Node.js は 20 以上を選ぶ。
3. 自分のパソコンで Codex を使うとき（CLI）も、最初に一度 `bash tests/setup.sh` を動かす。

### 最初の依頼文（コピー用）
```
AGENTS.md と docs/handoff.md を読んでください。そのうえで、
1. cd tests && npm test を動かし、結果を報告してください（件数も）。
2. docs/handoff.md の「いまの状態」と食い違うところがあれば、教えてください。
3. 「やり残し」のうち、次に取り組むとよいものを、理由とあわせて3つまで提案してください。
コードはまだ変えないでください。
```

### ふだんの頼み方
- 1つの依頼で、1つの変更（1つの PR）にする。
- 「AGENTS.md の約束と PR の書き方に従って」と添えると確実。
- PR が出たら、運営が中身を確かめる。ルールの変更がある PR は、**先にコンソールでルールを公開してから**マージする。
